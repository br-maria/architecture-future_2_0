# Task1 — Приоритизация проблем (MoSCoW) + связь с целями бизнеса

## Цели бизнеса (из задания)
- Через 2–3 месяца: согласовать архитектуру, определить домены и связи, запланировать проекты витрины данных.
- Через год: запустить портал самообслуживания, дать доменам работать в новой архитектуре; допускается временное сохранение легаси в отдельных доменах.

## MoSCoW (что нужно решить в первую очередь)
> Критерий «Must»: влияет на скорость отчётности / масштабирование / безопасность так, что без решения цели года недостижимы.

### Must have (критично, блокирует цель «портал + домены»)
- **P1 Монолитное DWH и сильная связанность** → без декомпозиции доменов и выноса аналитической платформы не получится масштабировать направления.
- **P2 Бизнес‑логика внутри DWH + тяжёлые кастомизации BI** → продолжит ломать time-to-market и порождать долгие отчёты.
- **P3 Устаревший SQL Server 2008 (масштаб/эластичность)** → не обеспечит приемлемую производительность на сотнях ТБ и росте пользователей.
- **P7 Нет Data Governance/каталога/метаданных** → self‑service невозможен (пользователь не найдёт данные и нельзя безопасно дать доступ).
- **P8 Риски ИБ и комплаенса** → при переносе в облако и росте экосистемы это главный риск для бизнеса.
- **P11 Нет наблюдаемости данных (DQ/lineage/мониторинг)** → без этого портал будет выдавать «сомнительные цифры», доверия не будет.

### Should have (очень важно, но можно частично закрыть временными решениями)
- **P5 ESB (Apache Camel) как bottleneck** → постепенно разгружать через event‑driven и API‑контракты.
- **P6 Нет data product подхода** → можно стартовать с ключевых доменных продуктов (финансы, продажи/выручка, операции клиник).
- **P9 PowerBuilder завязан на DWH** → допускается временно оставить в отдельных доменах, но нужен план «расцепления».

### Could have (желательно, но не критично для первой версии)
- **P10 Дублирование интеграций** → уменьшать по мере стандартизации через события/API.
- **P4 Много трансформаций для разных срезов** → значительная часть уйдёт после появления curated/serving зон и семантики, но оптимизация отдельных отчётов может быть поэтапной.
- **P12 Смешение клинических данных с аналитикой** → решается архитектурно (контуры/изоляция), но глубокая реорганизация может быть по шагам.

### Won’t have (в рамках года — сознательно откладываем)
- Полная остановка всех легаси и «big bang» миграция. В задании допускается временное сохранение легаси в отдельных доменах; фокус года — **портал + доменная модель + облачная платформа данных**.

## Как приоритизация связана с бизнес‑метриками
- **Выручка/скорость вывода финтех‑продуктов**: P1/P2/P5/P6 (независимость домена + быстрые изменения).
- **Скорость управленческих решений**: P2/P3/P4/P11 (скорость и качество отчётности).
- **Надёжность и комплаенс**: P8/P12/P7 (снижение рисков санкций/утечек).
- **Масштабирование на новые бизнесы (фарма/оборудование)**: P1/P5/P7 (подключение через контракты и стандарты).
