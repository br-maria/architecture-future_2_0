# Task2 — Домены и потоки данных (DFD) для поддержки ключевых бизнес‑сценариев

Файл диаграммы: `dfd_domains.png`.

## 1) Предлагаемое разбиение на домены

### Домены «ядра бизнеса»
1. **Клиники (Clinic Operations)**
   - Записи, услуги, факты оказания услуг, счета клиники, движения по складу клиники, первичные операционные события.
   - Важно: **PHI** (медкарты/истории/результаты исследований) остаётся в клиническом контуре и не идёт в аналитику.

2. **Финтех (Fintech/Banking)**
   - Счета банка, кредиты, транзакции, KYC/AML, финансовые события банка.

3. **ИИ (AI Services)**
   - Обучение/инференс моделей на медицинских данных в своём контуре.
   - В аналитику публикуются **только обезличенные/не‑PHI результаты** (например, агрегированные метрики качества, статусы обработок, признаки без персональных данных — по политике комплаенса).

4. **Партнёры (Partners Ecosystem)**
   - Интеграции с фармой и производителем оборудования: поставки, каталоги, рекомендации, сервисные события оборудования, B2B контракты.

### Домены «общих корпоративных функций»
5. **Идентичность / MDM**
   - Единые справочники (клиент, договор, контрагент, клиника, продукт/услуга).
   - Снимает проблему «разных идентификаторов» при росте экосистемы.

6. **Биллинг (Billing)**
   - Начисления, платежи, возвраты, выставление счетов, связка «медицинская услуга ↔ финансовая операция».
   - Отделение биллинга от DWH убирает необходимость «дописывать логику в DWH» под новые продукты.

7. **Корпоративный домен (Corporate)**
   - HR, управленческий учёт, финансовая отчётность, KPI управления клиниками (без PHI).

8. **Снабжение/Склад (Supply & Inventory)**
   - Закупки, остатки, складские движения, оборудование (в т.ч. сервисные циклы).

### Платформенные домены (сквозные)
9. **Интеграционная платформа**
   - API Gateway + Event Streaming + Schema Registry.
   - Даёт стандартизированное подключение новых доменов и партнёров (без «точечных интеграций»).

10. **Платформа данных (Lakehouse)**
   - Raw/Curated/Serving зоны.
   - Хостинг **доменных data products** для аналитики и витрины данных.

11. **Governance & Security**
   - IAM (RBAC/ABAC), DLP, шифрование, аудит, lineage, каталог данных.
   - Критично для совместного использования финансовых и медицинских данных в облаке.

12. **Витрина данных / Семантический слой / BI**
   - Self-service портал: каталог, поиск, доступы, конструктор.
   - Семантика: единые метрики, RLS, бизнес‑глоссарий.
   - Power BI: дашборды и ad-hoc.

## 2) Потоки данных между доменами (что показывает DFD)

### Основной принцип обмена
- Между доменами ходят **контрактованные данные** через:
  - **API** (синхронные запросы) — когда нужна транзакционная согласованность/оперативная проверка.
  - **События** (асинхронно) — когда важна слабая связанность и масштабирование.
- Для аналитики домены публикуют **data products** в Lakehouse (Curated/Serving).

### Типовые потоки
- **Клиники → Интеграция → Billing/MDM → Lakehouse**
  - события оказания услуг, выставление счета, статусы оплат.
- **Fintech → Интеграция → Billing/MDM → Lakehouse**
  - транзакции, статусы кредитов, KYC‑события (в нужном для аналитики виде).
- **Partners → Интеграция → Supply/Inventory (+ Clinic) → Lakehouse**
  - поставки, каталоги, сервисные события оборудования, статусы заказов.
- **AI (в клиническом контуре PHI) → Интеграция → Lakehouse**
  - только результаты без PHI (агрегаты/метрики/статусы), строго через Governance.

## 3) Как бизнес‑сценарии обеспечиваются потоками данных

### Сценарий A: подключение нового финтех‑сервиса (быстрый time‑to‑market)
1. Новый сервис публикует события в **Event Bus** и/или предоставляет API через **API Gateway**.
2. Домен **Billing** подписывается на события/использует API и реализует правила начислений/платежей у себя (не в DWH).
3. Данные публикуются как **data product** (Serving) в Lakehouse.
4. Витрина/BI сразу используют новый продукт через семантический слой.

**Эффект:** изменения локализованы в домене, DWH не требуется «допиливать» — быстрее вывод продукта.

### Сценарий B: использование ИИ для анализа медданных
1. PHI (медкарты/исследования) остаются в клиническом контуре и доступны **только** доменам Clinic/AI.
2. AI‑домен выполняет inference и возвращает в клинический домен результат для лечения (операционный сценарий).
3. Для аналитики AI‑домен публикует **не‑PHI** артефакты (метрики, статусы, агрегаты) через интеграцию → Lakehouse.
4. Governance применяет политики маскирования/доступов и аудит.

**Эффект:** ИИ развивается независимо, комплаенс соблюдён, аналитика получает полезные метрики без PHI.

### Сценарий C: интеграция фармы и производителя оборудования
1. Партнёры подключаются через API GW и/или события.
2. Домен Supply/Inventory получает каталоги/поставки/сервисные события; клиники получают статусы оборудования.
3. В Lakehouse публикуются продукты для аналитики (затраты, остатки, эффективность оборудования).
4. Витрина данных масштабируется добавлением нового домена/продукта, без переделки DWH.

**Эффект:** расширение экосистемы без «комбинаторного взрыва» интеграций.

## 4) Почему такое разделение помогает бизнесу

- **Независимость развития направлений:** домены владеют своей логикой и данными; изменения не требуют правок монолитного DWH.
- **Снижение зависимости от DWH:** DWH превращается в временный источник/наследие; аналитика строится на Lakehouse + data products.
- **Ускорение time-to-market:** новые продукты подключаются через API/Event Bus, а аналитика — через публикацию data product.
- **Единые KPI и доверие к данным:** семантика + MDM + governance уменьшают «разные цифры в разных отчётах».
- **Комплаенс и ИБ:** PHI отделён, доступы централизованы, есть аудит и DLP — безопаснее при переезде в облако.
